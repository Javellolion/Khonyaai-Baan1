## 1. Intent
ผู้ใช้บริการที่จองรถขนย้ายสิ่งของสำเร็จแล้ว ต้องยกเลิกการจองได้ก่อนเวลานัดหมาย (AC: ผู้ใช้ที่มีธุระด่วนกะทันหัน)
เหตุผล (REQ-CMP-001): กำหนดหลักเกณฑ์การยกเลิกและค่าปรับให้ชัดเจน ลดความเสียหายจากการยกเลิกกะทันหัน และให้เป็นธรรมทั้งลูกค้าและผู้ให้บริการ
หลักฐาน: EV-006 (คุณมอส, สัมภาษณ์ 45 นาที, Opinion, Low, สถานะ "รอตรวจสอบเพิ่ม") — ตารางตรวจ Use Case ระบุ UC "ลูกค้ายกเลิกการจอง" สอดคล้องกับ EV-006 และควรรวมการคำนวณค่าปรับหรือหักมัดจำ
บริบทปัญหาระดับโครงการ (ตาราง 7 คำถามนำ) ที่เกี่ยวกับการยกเลิก:
- ผลกระทบที่วัดได้: ค่าใช้จ่ายนอกเหนือจากที่ตกลง และการโดนยกเลิกโดยไม่รู้สาเหตุ
- ตัวชี้วัดว่าแก้แล้ว: ผู้ใช้รู้ราคาแน่นอนและไม่มีค่าใช้จ่ายแฝง
ปัญหาเชิงตัวเลข/สถิติที่เกี่ยวข้อง: [ไม่มีข้อมูล ต้องเติมโดยกลุ่ม] (ตาราง 7 คำถามนำไม่มีค่าปัจจุบัน/ค่าเป้าหมาย/กรอบเวลา)

## 2. Scope & Non-goals
In:
- ลูกค้ายกเลิกการจองก่อนคนขับกดรับงาน
- ลูกค้ายกเลิกการจองหลังคนขับกดรับงาน ก่อนถึงเวลานัดหมาย
- คืน/ริบเงินมัดจำตามเงื่อนไข และแจ้งผลให้ลูกค้าและคนขับ
- กรณีนอกกฎที่กำหนด ส่งให้แอดมินตรวจสอบตามนโยบายองค์กร (ตามแผนภาพ Activity/State Machine)
ขอบเขตระดับโครงการ (ตาราง Inscope) ที่เกี่ยวข้อง: ผู้ใช้ — ระบบจองบริการ, ประวัติการจอง, Tracking, Chat | Admin — ดูรายการจอง | คนขับ — รับงาน, ปฏิเสธงาน, เปลี่ยนสถานะงาน
(ตาราง Inscope ไม่มีคำว่า "ยกเลิก" โดยตรง)
Non-goals ระดับโครงการ (ตาราง Outscope — กลุ่มต้องยืนยันว่าใช้กับสเปกนี้):
- ประกันสิ่งของเสียหายในเฟสแรก
- การตรวจสอบประวัติคนขับ
- การบริการพื้นที่นอกกรุงเทพฯ–ปริมณฑลในเฟสแรก
Non-goals (R1) เฉพาะการยกเลิก: [ไม่มีข้อมูล ต้องเติมโดยกลุ่ม]

**ลำดับการทำงาน (จาก Sequence/Activity Diagram)**
1. ลูกค้าเลือกรายการจอง → ระบบแสดงรายละเอียดและเงื่อนไขการยกเลิก → ลูกค้าระบุเหตุผลและยืนยัน
2. ระบบตรวจสิทธิ์และสถานะการจองล่าสุด (validateCancellation)
3. แยกตามเงื่อนไข:
   - เงื่อนไข 1: ยังไม่มีคนขับรับงาน → สถานะ CANCELLED_FULL_REFUND → ส่งคำขอคืนมัดจำไป Payment Gateway → ได้ผลสำเร็จและเลขอ้างอิง
   - เงื่อนไข 2: คนขับรับงานแล้วและเหลือเวลา ≤ 2 ชม. → สถานะ CANCELLED_DEPOSIT_FORFEITED → แจ้งคนขับ (bookingId, depositPolicy)
   - เงื่อนไข 3: เริ่มงานแล้วหรือสถานะไม่อนุญาต → ปฏิเสธคำขอ (cancellationRejected)
   - คนขับรับงานแล้วแต่เวลาที่เหลือไม่ใช่ ≤ 2 ชม. / นโยบายยังไม่กำหนด (ป้าย "ไม่ใช่ / นโยบายยังไม่กำหนด" ใน Activity Diagram) → ส่งแอดมินตรวจสอบตามนโยบายองค์กร → อนุมัติคืนเงิน (ส่งคำขอคืนมัดจำ) หรือไม่อนุมัติ (บันทึกผลตามคำวินิจฉัย)
   - คืนเงินไม่สำเร็จ → ส่งให้แอดมินติดตาม (State Machine มี retryRefund)
4. ระบบแจ้งผล (สถานะ เงินมัดจำ เลขอ้างอิง) ให้ลูกค้าและคนขับ

**Job lifecycle (State Machine "ลูกค้ายกเลิกการจอง")**
- สถานะหลัก: การจองมีผล | ร้องขอยกเลิกแล้ว | ปฏิเสธการยกเลิก | ยกเลิกแล้ว
- สถานะย่อยใน "ประมวลผลการยกเลิก": ตรวจสอบคำขอ | ประเมินนโยบายยกเลิก | รอแอดมินตรวจสอบนโยบาย | ยกเลิกแบบคืนมัดจำเต็มจำนวน | กำลังคืนเงิน | คืนเงินไม่สำเร็จ | ยกเลิกและริบมัดจำ | แจ้งผลให้ลูกค้าและคนขับ
- ชื่อสถานะแบบ code ใน Sequence: CANCELLED_FULL_REFUND, CANCELLED_DEPOSIT_FORFEITED

## 6. Acceptance Criteria -> features/cancel.feature
AC-ID: AC-01-01, AC-01-02, AC-01-03

AC-01-01: ยกเลิกก่อนคนขับรับงาน
> ในฐานะลูกค้าที่มีธุระด่วนกะทันหัน หลังจากจองบริการไปแล้ว ฉันต้องการให้สามารถยกเลิกการจองบริการได้ก่อนคนขับกดรับงาน เพื่อให้ได้รับคืนมัดจำเต็ม
> Given ลูกค้ามีงานด่วนกะทันหันหลังจากจองบริการแล้ว | And ลูกค้าเสียค่ามัดจำแล้ว | And ยังไม่มีคนขับรับงาน
> When ลูกค้ายกเลิกการบริการ
> Then สถานะการจองต้องเป็น "ยกเลิกแล้ว" | And ระบบคืนเงินมัดจำ 100% | And ระบบแจ้งเตือนลูกค้าและผู้ให้บริการ

AC-01-02: ยกเลิกหลังคนขับรับงานและก่อนถึงเวลา 2 ชั่วโมง
> ในฐานะลูกค้าที่มีธุระด่วนกะทันหัน ฉันต้องการยกเลิกการจองได้หลังคนขับรับงานแล้วและก่อนถึงเวลานัดหมาย 2 ชั่วโมง เพื่อให้ทราบว่าต้องเสียมัดจำตามนโยบาย
> Given ลูกค้ายังไม่เริ่มงาน | And ผู้ให้บริการยืนยันรับงานแล้ว | And เหลือเวลาถึงเวลานัดหมายไม่เกิน 120 นาที
> When ลูกค้ายกเลิกการบริการ
> Then สถานะการจองต้องเป็น "ยกเลิกแล้ว" | And ผู้ใช้บริการเสียค่ามัดจำ 100% | And ระบบแจ้งเตือนไปที่ผู้ให้บริการ

AC-01-03: ยกเลิกกรณีที่ต้องส่งแอดมินพิจารณา

## 8. Constraints
REQ-CON-001 (เฉพาะการยกเลิก): ต้องปฏิบัติตามนโยบายคืน/ริบมัดจำและการคุ้มครองข้อมูลส่วนบุคคลตามแนวทางที่กำหนดไว้ในสเปกนี้
ข้อจำกัดระดับโครงการ (ตาราง Constraints — ต่อรองไม่ได้):
- REQ-CON-001A: ต้องสอดคล้อง PDPA เพราะเก็บเลขบัตรประชาชนและที่อยู่บ้าน
- REQ-CON-001B: ต้องเก็บหลักฐานการยืนยันตัวตนตามระยะเวลาที่กฎหมายกำหนด
- REQ-CON-001C: ต้องไม่เก็บสำเนาบัตรประชาชนเมื่อยืนยันตัวตนผ่าน Thai-ID ได้แล้ว (หลักการเก็บเท่าที่จำเป็น)
- REQ-CON-001D: Frontend ต้องใช้ React + Vite + Tailwind ในการสร้างหน้าจอยกเลิกการจองและผลลัพธ์
- REQ-CON-001E: Backend ต้องใช้ FastAPI สำหรับ API ยกเลิกการจองและผสาน Payment Gateway
- REQ-CON-001F: ฐานข้อมูลต้องใช้ PostgreSQL สำหรับจัดเก็บข้อมูลการจอง, สถานะ, ผลการคืน/ริบมัดจำและ log การตรวจสอบ
(หมายเหตุ: เกณฑ์ 2 ชม./120 นาที อยู่ใน Business rules ส่วน 5)
